# Архитектурное предложение для проекта vuz-hub-proj

## 1. Краткий вывод

Сейчас проект выглядит как хорошо организованный модульный монолит, а не как чистый микросервисный продукт. Внутри backend есть смысловая структура по доменам (`users`, `groups`, `schedules`, `subjects`, `debts`, `dops`, `auth`), а также присутствуют признаки будущего выделения сервисов: `source/backend/msa/auth_service`, `source/backend/msa/generate_service` и отдельный `source/proxy` на Rust.

Это хороший сигнал: архитектура уже движется в сторону сервисного разбиения, но пока ещё не разделена по реальным границам владения данными и ответственности.

Главный тезис:

- Не делать один общий "micro-core"/"shared service", который знает про пользователей, расписание, долги, генерацию и уведомления.
- Не ставить в общий сервис БД, драйверы и общий доступ к данным.
- Делать платформенную инфраструктуру и отдельные доменные сервисы.


## 2. Почему не стоит делать одно общее "ядро"

### Что плохого в таком решении

Если сделать единый сервис, в котором хранится:
- общая БД
- общие драйверы к внешним системам
- логика auth
- логика генерации расписания
- работа с пользователями
- долги и уведомления

то это станет не микросервисной архитектурой, а новой версией монолита.

Проблемы:
- одна точка слияния всех изменений
- сложные зависимости между доменами
- рост связанности и нагрузка на один сервис
- сложность масштабирования отдельных частей
- один сервис превращается в “все-в-одном”


## 3. Правильное разделение: platform + domain services

Нужно разделять:

### 3.1 Platform / Infrastructure layer
Это общий слой, который не знает про бизнес-данные, а только про инфраструктуру.

Что туда относим:
- API Gateway / Rust proxy
- service discovery
- secrets/config management
- observability: logs, tracing, metrics
- auth token validation library
- shared HTTP clients / retry policies / timeouts
- shared event contracts / schemas / DTO interfaces
- message broker client libs
- common errors / idempotency helpers

Это слой, который обеспечивает нормальную работу системы, но не владеет бизнес-данными.

### 3.2 Domain services
Это уже бизнес-сервисы, каждый со своей областью ответственности.

Пример:
- Auth Service
- User & Profile Service
- Academic Service
- Schedule Service
- Generator Service
- Dean Office / Debts Service
- Notification Service
- Telegram Adapter / Bot Service

Каждый сервис:
- владеет своей БД
- владеет своей моделью данных
- работает по своей предметной области
- общается через API или события


## 4. Рекомендуемая архитектура для этого проекта

### 4.1 Внешний слой
- Rust Proxy / Gateway
- служит входом для внешнего трафика
- маршрутизирует запросы между сервисами
- выполняет базовую аутентификацию / фильтрацию / rate limiting
- не содержит бизнес-логики

### 4.2 Platform services
- Auth / Identity
- Config / Secrets
- Event Bus / Messaging
- Observability
- Discovery / Service registry

### 4.3 Бизнес-сервисы

#### 1) Auth & Identity Service
Ответственность:
- пользователи
- роли
- JWT
- логин/логаут
- social binds: TG/VK/MAX
- session и access control

Почему выделять первым:
- это базовый слой, от которого зависят все остальные
- это уже явно прописано в backend/readme.md и в модели `User`, `UserRole`, JWT

#### 2) Academic / Profile Service
Ответственность:
- группы
- предметы
- связи студент-предмет
- учёба и профили

#### 3) Schedule Service
Ответственность:
- расписание
- слоты
- учебные события
- запросы расписания

#### 4) Generator Service
Ответственность:
- генерация расписания
- алгоритмы и оптимизация
- асинхронные задачи и jobs
- результаты генерации

Это очень хороший кандидат для отдельного сервиса, потому что процесс генерации тяжёлый и вычислительный.

#### 5) Dean Office / Records Service
Ответственность:
- долги
- dops
- нарушения
- академические записи

#### 6) Notification Service
Ответственность:
- отправка сообщений студентам и преподавателям
- Telegram / email / SMS / VK
- шаблоны
- статусы отправки
- retry / dead letters

#### 7) Telegram Adapter / Bot Service
Ответственность:
- общение с Telegram
- обработка команд
- адаптация блоков под backend API

Это может быть отдельным сервисом или адпаттером вокруг бота, но лучше вынести отдельно от бизнес-модели.


## 5. Как строить взаимодействие между сервисами

Нужно избегать “вызовов по всем данным напрямую между сервисами”.

### 5.1 Основной стиль
- REST/gRPC для синхронных запросов
- события в брокере для асинхронной интеграции

### 5.2 Примеры событий
- `user.created`
- `user.role.updated`
- `group.assigned`
- `schedule.generated`
- `debt.created`
- `notification.sent`
- `notification.failed`

### 5.3 Контракты
Нужны общие схемы/контракты:
- event envelope
- common id types
- user identity payload
- notification payload
- schedule generation result

Это уже ближе к платформенной инфраструктуре, а не к “общему сервису-ядру”.


## 6. Почему платформенный слой лучше, чем общий сервис

### Плюсы платформенного слоя
- нет единой точки слияния бизнес-логики
- не возникает “монолит в контейнерах”
- проще масштабировать сервисы независимо
- проще развивать команды
- меньше уязвимостей из-за общих зависимостей
- лучше изоляция данных и ответственности

### Потенциальные ошибки, которых нужно избегать
- общая БД на уровне платформы
- общий слой, который знает про все сущности
- бизнес-логику в gateway
- единая схема данных на весь проект
- “shared core” со всеми доменами внутри


## 7. Рекомендуемая стартовая схема для проекта

Если проект сейчас не готов к полному разделению, лучше двигаться так:

### Этап 1 — gateway + auth + generator + notifications
- Rust proxy как API Gateway
- Auth Service отделён от монолита
- Schedule Generator выделен в отдельный сервис
- Notification Service выделен отдельно
- Остальные домены остаются в backend-монолите

### Этап 2 — выделение academic profile и dean office
- Academic Service
- Dean Office Service

### Этап 3 — разделение Telegram и API adapter
- bot как отдельный внешний слой / adapter service

Такой подход уменьшает риск, сохраняет управляемость и не создаёт “суперсервис”, который в итоге станет новой монолитной системой.


## 8. Итоговая архитектурная идея

Правильная формулировка:

- Не делать core service с общей логикой и общей БД.
- Делать platform infrastructure + domain services.
- Gateway на Rust — это ingress, не бизнес-ядро.
- Общая инфраструктура — config, auth libs, tracing, broker, schemas, gateway.
- Бизнес-логика — в отдельных сервисах по доменам.

То есть архитектура должна строиться так:

- API Gateway
- Shared platform / infrastructure
- Domain services
- Event-driven integration
- Separate databases per service

Это даёт стабильность, масштабируемость и отсутствие “централизованного монолита в новом виде”.


## 9. Резюме

Сейчас проект уже на грани “модульного монолита”, а не “чистого монолита”. Это нормально. Ваша главная задача — не создать ещё один глобальный сервис, а провести правильную границу ответственности.

Правильная стратегия:

- gateway на Rust — yes
- shared platform — yes
- shared business core — no
- one common DB for all services — no
- one central service knowing about all domains — no

Если сделать всё так, проект будет расти намного здоровее, чем если строить “общее микро ядро”.


## 10. Короткая формула для команды

“Micro-core” = плохой паттерн, если он бизнес-центрирован.
“Platform layer” + “domain services” = правильный паттерн.

Где:
- gateway = ingress
- platform = infrastructure
- services = business domains
- broker + events = communication
- separate DBs = isolation
