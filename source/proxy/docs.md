# HTTP Reverse Proxy

Небольшой асинхронный обратный прокси на Rust (Hyper + Tokio) с маршрутизацией по префиксу пути и конфигурацией через TOML.

## Возможности

- Маршрутизация входящих запросов по префиксу пути к разным upstream-серверам.
- Выбор наиболее специфичного (самого длинного) маршрута с проверкой границы сегмента.
- Опциональное отсечение префикса при проксировании (`strip_prefix`).
- Проброс query-строки, метода и тела запроса (тело стримится без буферизации).
- Корректная обработка hop-by-hop заголовков (включая перечисленные в `Connection`).
- Установка заголовков `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`.
- Таймаут обращения к upstream.
- Логирование каждого запроса в stderr.
- Мягкое завершение по `Ctrl+C`.

## Запуск

```bash
cargo run --release -- config.toml
```

Если путь к конфигу не указан, используется `config.toml` в текущем каталоге.

## Конфигурация

Конфигурация — файл TOML следующего вида:

```toml
# Адрес и порт, на котором слушает прокси
listen = "127.0.0.1:8080"

# Таймаут запроса к upstream в секундах (по умолчанию 30)
upstream_timeout_secs = 30

# Список маршрутов
[[routes]]
prefix = "/api"
upstream = "http://127.0.0.1:9001"
strip_prefix = false

[[routes]]
prefix = "/api/v2"
upstream = "http://127.0.0.1:9002/base"
strip_prefix = true
```

### Поля конфигурации

#### `Config`

| Поле                    | Тип      | Обязательно | По умолчанию | Описание                                   |
|-------------------------|----------|-------------|--------------|--------------------------------------------|
| `listen`                | string   | да          | —            | Адрес прослушивания (`host:port`).         |
| `upstream_timeout_secs` | integer  | нет         | `30`         | Таймаут запроса к upstream в секундах.     |
| `routes`                | array    | да          | —            | Список маршрутов (см. ниже).               |

#### `RouteConfig`

| Поле           | Тип     | Обязательно | По умолчанию | Описание                                                                 |
|----------------|---------|-------------|--------------|--------------------------------------------------------------------------|
| `prefix`       | string  | да          | —            | Префикс пути; должен начинаться с `/`.                                   |
| `upstream`     | string  | да          | —            | URL upstream вида `http://host[:port][/base_path]`. Поддерживается только `http`. |
| `strip_prefix` | boolean | нет         | `false`      | Если `true`, совпавший префикс отсекается перед отправкой в upstream.     |

### Правила маршрутизации

1. Из всех маршрутов выбирается тот, чей `prefix` совпадает с началом пути запроса **по границе сегмента**. Совпадение по границе означает одно из:
   - путь полностью равен префиксу;
   - следующий символ после префикса — `/`;
   - сам префикс заканчивается на `/`.
2. Если подходят несколько маршрутов, побеждает самый длинный префикс (маршруты сортируются по убыванию длины при старте).
3. Если ни один маршрут не подошёл — ответ `404 Not Found`.

### Формирование целевого URI

Пусть у маршрута `base_path` — путь из `upstream` без завершающего `/` (может быть пустым), `tail` — остаток пути запроса:

- при `strip_prefix = true` — `tail` = часть пути после префикса;
- при `strip_prefix = false` — `tail` = весь исходный путь.

Итоговый путь вычисляется как конкатенация `base_path` + `/` (при необходимости) + `tail`, затем добавляется исходная query-строка. Схема и authority берутся из `upstream`.

Примеры (для `upstream = "http://backend:9000/base"`):

| prefix    | strip_prefix | Входящий путь     | Итоговый путь к upstream |
|-----------|--------------|-------------------|---------------------------|
| `/api`    | `false`      | `/api/users?x=1`  | `/base/api/users?x=1`     |
| `/api`    | `true`       | `/api/users?x=1`  | `/base/users?x=1`         |
| `/api`    | `true`       | `/api`            | `/base/api`               |
| `/api/v2` | `true`       | `/api/v2/items`   | `/base/items`             |

## Обработка заголовков

### Hop-by-hop заголовки

Перед отправкой в upstream и перед возвратом клиенту из запроса/ответа удаляются:

- `connection`
- `keep-alive`
- `proxy-authenticate`
- `proxy-authorization`
- `te`
- `trailer`
- `transfer-encoding`
- `upgrade`

Дополнительно удаляются заголовки, перечисленные в значении `Connection`.

### Добавляемые заголовки (запрос к upstream)

| Заголовок           | Значение                                                                 |
|---------------------|--------------------------------------------------------------------------|
| `Host`              | authority из `upstream`.                                                 |
| `X-Forwarded-For`   | IP клиента; если заголовок уже был — к нему дописывается `, <ip>`.       |
| `X-Forwarded-Host`  | исходный `Host` запроса (или authority из URI, если `Host` отсутствует). |
| `X-Forwarded-Proto` | всегда `http`.                                                           |

Версия запроса к upstream принудительно устанавливается в `HTTP/1.1`.

## Ошибки

| Ситуация                              | HTTP-статус          | Тело ответа        |
|---------------------------------------|----------------------|--------------------|
| Нет подходящего маршрута              | `404 Not Found`      | `no route`         |
| Превышен таймаут обращения к upstream | `504 Gateway Timeout`| `upstream timeout` |
| Ошибка соединения/запроса к upstream   | `502 Bad Gateway`    | `bad gateway`      |

Подробности ошибок upstream пишутся в stderr.

## Архитектура кода

| Компонент | Назначение |
|-----------|------------|
| `Config`, `RouteConfig` | Десериализация TOML-конфигурации. |
| `Route` | Разобранный маршрут: префикс, флаг `strip_prefix`, схема, authority, `base_path`. |
| `Route::from_config` | Валидация и разбор одного маршрута. |
| `pick_route` | Выбор наиболее специфичного маршрута с проверкой границы сегмента. |
| `State` | Общее состояние: отсортированные маршруты, HTTP-клиент, таймаут. |
| `ProxyError` | Ошибки проксирования и преобразование их в HTTP-ответ. |
| `strip_hop_by_hop` | Удаление hop-by-hop заголовков. |
| `proxy` | Основная логика: маршрутизация, переписывание URI/заголовков, запрос к upstream. |
| `handle` | Обёртка над `proxy` с логированием и преобразованием ошибок. |
| `main` | Загрузка конфигурации, инициализация состояния, accept-loop, обработка `Ctrl+C`. |

## Ограничения

- Поддерживается только `http://` для upstream (TLS не реализован).
- Прокси сам обслуживает только HTTP/1.1 (клиентские соединения и соединения к upstream).
- Нет встроенной аутентификации/авторизации, rate limiting, health-check'ов.
- Тело запроса и ответа стримятся, но таймаут применяется только к получению заголовков ответа от upstream.

## Пример

```bash
# config.toml
listen = "0.0.0.0:8080"

[[routes]]
prefix = "/"
upstream = "http://127.0.0.1:3000"
strip_prefix = false
```

```bash
cargo run --release -- config.toml
# proxy listening on http://0.0.0.0:8080
curl -v http://localhost:8080/hello
```
